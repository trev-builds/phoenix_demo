# Challenges and how I solved them

1. **Real export didn't match the expected filename, and wasn't git-ignored.** The code expected `data/activities.csv`, but my export was `data/trev_gamin.csv`, and `.gitignore` only covered the first name. Fix: set `CSV_PATH` in `.env` and changed `.gitignore` to `data/*.csv` so no personal data can be committed.
2. **Python 3.9 limits the Phoenix version.** pip resolved `arize-phoenix` 12.15.1 (newer releases need Python 3.10+). Fine for this project, but the docs describe the newest client, so expect API differences (see below).
3. **Garmin export has junk activities.** One "run" has 0.00 mi (dropped by `data.py`), and ~7 are 0.1–0.5 mi / ~1 minute (accidental starts or warm-ups). I kept them: ground truth and tools see the same rows, so the A-vs-B comparison stays fair, but they shift "average run distance" and per-run averages. Noted as a data limitation, not filtered.


4. **Tiny runs would distort aerobic efficiency.** Period efficiency averages per-run values, so a 1-minute accidental run counts as much as a 6-mile run. Decision: the efficiency definition only counts runs >= 1.0 mi with HR data, and every question says so.


5. **Verified efficiency ground truth two ways.** pandas (`ground_truth.py`) and a separate plain-`csv` script agree to 4 decimals (Aug 4.8836, Sep 4.8631, Jul 4.8817).
6. **My real efficiency barely moved, which makes the questions fragile.** July vs August differs by 0.002, so the "improve Jul→Aug?" answer (yes) depends on noise, and anyone who rounds to 2 decimals first sees a tie. The Sep−Aug change (−0.02) equals the 0.02 tolerance, so an answer of 0.00 also scores correct.
7. **Fix for #6: compared periods far enough apart to show a real change.** Swapped the Jul/Aug/Sep comparisons for April→August (+0.31) and May→September (+0.17), which are well clear of noise and tolerance. The 8-week question (−0.03) is still near the tolerance, so it's a known weak item.
8. **`agent.py` sent no traces when run by itself.** Only `run_experiments.py` and the notebook called Phoenix's `register()`. Added it to `agent.py`'s `__main__` block so single test runs are traced without affecting experiments.
9. **Phoenix project setup was confusing.** The UI onboarding asked me to pick an integration ("Claude Agent SDK"), but this agent uses the plain Anthropic SDK, traced by `openinference-instrumentation-anthropic`. The UI choice only changes the setup snippet it shows. Phoenix creates the project automatically from `register(project_name=...)`, so traces land in `garmin-run-agent`.

## Phoenix API mismatches (scaffold vs installed arize-phoenix 12.15.1 / arize-phoenix-client 1.31.0)
10. **`px.Client()` is deprecated and doesn't read `PHOENIX_API_KEY` from the environment**, so it couldn't authenticate to Phoenix Cloud. Switched to `from phoenix.client import Client`, which reads `PHOENIX_API_KEY` + `PHOENIX_COLLECTOR_ENDPOINT` automatically.
11. **Methods moved under resource namespaces:** `upload_dataset(dataset_name=)` became `client.datasets.create_dataset(name=)`, `get_dataset(name=)` became `client.datasets.get_dataset(dataset=)`, and `phoenix.experiments.run_experiment(dataset, task)` became `client.experiments.run_experiment(dataset=, task=)` (keyword-only).
12. **Scaffold bug: answer key was nested twice.** It packed `{expected, tolerance, kind}` into a column also named `expected`, so the evaluator got `expected["expected"]["expected"]` and would crash. Fixed by uploading them as three flat output keys.
13. **Dataset upload turned numbers into strings.** The `expected` column mixes numbers and "yes"/"june", so the dataframe upload stored `'18.51'` and `'0.06'` as text, and the evaluator crashed comparing a float to a string. Found with `dry_run=1` (runs 1 example, records nothing). Fix: cast in the evaluator. **Learning: always dry-run an experiment before paying for a full run.**
14. **`load_dotenv()` crashes when Python reads a script from stdin** (`find_dotenv` assertion). Pass the path explicitly: `load_dotenv(".env")`.
15. **Couldn't find the experiment traces.** Each experiment writes its traces to its own auto-created project (`Experiment-d7937...` for A, `Experiment-7668...` for B). These are hidden from the Projects list, and `garmin-run-agent` only holds my manual test runs. Found them with `client.spans.get_spans_dataframe(project_name=...)`. In the UI, you reach them from Datasets → Experiments → click a run's trace icon, or directly at `/projects/<id>`.
16. **Diagnosing failures needed more than the score.** A 0/1 score doesn't say *why*. I parsed the numbers the model wrote in each wrong answer and checked two things separately: (a) did it list the right rows (date logic), and (b) did those rows add up to what it claimed (arithmetic). That split every failure cleanly.
17. **No readable question numbers in Phoenix.** The upload only sent question text + answer key, and Phoenix shows base64 example IDs (`RGF0YXNldEV4YW1wbGU6NA==` = `DatasetExample:4`). For v2, add a `qid` (and `group`) via `metadata_keys` at upload. Lesson: give every dataset example a human-readable ID from the start.
18. **Evals showed only 0/1 in Phoenix, with no reason.** The evaluator returned just the score. Changed `answer_correct` to return `{score, label, explanation}` and re-scored the existing experiments with `client.experiments.evaluate_experiment()` (`reevaluate.py`), with no new Claude calls. Added as `answer_correct_explained` beside the original; all 44 scores match.
